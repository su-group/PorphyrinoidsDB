# `data/` — source table, feature caches, frozen splits

Everything in this directory is an input. Nothing here is regenerated by the package itself
except the two feature caches, which are shipped so that a reader can reproduce every number in
[../README.md](../README.md) without spending hours on Mordred.

| File | Bytes | Role |
| --- | ---: | --- |
| `Data-20261012.csv` | 1,374,196 |  | Source table: one row per DFT calculation, 57 columns |
| `Data-20261012_raw_features.csv` | 36,413,325 |  | Mordred descriptor cache for the 1,734 valid molecules (1,613 columns) |
| `Data-20261012_raw_features.csv.meta.json` | 746,186 |  | Cache manifest for the file above |
| `Data-20261012_raw_features_fp.csv.xz` | 11,467,720 |  | Fingerprint cache (65,512,409 B raw) shipped LZMA-compressed |
| `Data-20261012_raw_features_fp.csv.meta.json` | 924,865 |  | Cache manifest for the file above |
| `splits-20261021.json` | 549,089 |  | Frozen train/test splits and CV folds for all three axes |

The three `data_sha256` fields inside the cache manifests and the split manifest all point at the
same source table, so the provenance chain is closed: **source CSV → cache → split →
model**. If you edit `Data-20261012.csv`, every loader in `core/` refuses the caches.

Decompress the fingerprint cache before using it:

```bash
python -c "import lzma,shutil; shutil.copyfileobj(lzma.open('Data-20261012_raw_features_fp.csv.xz','rb'), open('Data-20261012_raw_features_fp.csv','wb'))"
# 65,512,409 bytes
```

That decompressed copy is the exact file the matching `.meta.json` was built from;
`../analysis/check_cache_integrity.py` re-verifies the round trip.

## 1. The source table

`Data-20261012.csv` holds **1,860 records** plus a header line. Each record is one DFT calculation
on one `A–X–B–C` combination (a porphyrin-like `A` core, a bridging `X`, a meso substituent `B`, an
axial ligand count `C`) and reports its HOMO–LUMO gap in eV.

### Columns

| Group | Columns |
| --- | --- |
| Identifiers / design factors | `idx`, `SMILES`, `A_number`, `X_element`, `B_number`, `C_number`, `Y_number` |
| Status | `Status` |
| **Target** | `Gap(eV)` |
| DFT orbital energies | `HOMO-3(eV)` … `HOMO(eV)`, `LUMO(eV)` … `LUMO+3(eV)`, `SCF Done(Hartree)` |
| Optical | `Q band (nm)`, `S band (nm)` |
| Physicochemical descriptors | `MolecularWeight`, `ExactMolWt`, `LogP`, `LogS`, `NumHDonors`, `NumHAcceptors`, `TPSA`, `NumRotatableBonds`, `NumHeavyAtoms`, `NumAtoms`, `NumBonds`, `NumRings`, `NumAromaticRings`, `NumHeterocycles`, `MolMR`, `WienerIndex` |
| Topological / QSPR | `Chi0` … `Chi4`, `BoilingPoint(K)`, `MeltingPoint(K)`, `VaporPressure(Pa)`, `Density(kg/m3)`, `CriticalTemperature(K)`, `CriticalPressure(Pa)`, `CriticalVolume(m3/mol)` |
| Conceptual DFT (target-derived — see warning) | `ElectronAffinity(eV)`, `IonizationPotential(eV)`, `ChemicalPotential(eV)`, `ChemicalHardness(eV)`, `ChemicalSoftness(1/eV)`, `ElectrophilicityIndex`, `NucleophilicityIndex`, `Electronegativity(eV)`, `Energy Min` |

### Filtering: 1,860 → 1,734

`core/data_processing.py` (`load_valid_data`, line 23) keeps a row only if

```
C_number ∈ {0, 1, 2}  ∧  Status == 'Structure Optimization Finished'
∧  isfinite(Gap(eV))  ∧  Gap(eV) > 0
```

In practice the `Status` test does all the work — exactly 1,734 of the 1,860 rows carry it:

| `Status` | Rows |
| --- | ---: |
| `Structure Optimization Finished` | **1,734** |
| `Imaginary Frequencies` | 47 |
| `l9999` | 42 |
| `File Not Found` | 30 |
| `l502` | 3 |
| `Incomplete` | 2 |
| `l103` | 2 |

All 1,734 survivors also have `C_number ∈ {0,1,2}` (984 / 438 / 438 over the full table), a finite
positive gap and a normalisable SMILES, so no further row is lost. The surviving rows are what every
cache, split and model in this package indexes by position `0…1733`.

### Leakage warning — target-derived columns

Nine columns are exact algebraic functions of `HOMO(eV)` and `LUMO(eV)`, and therefore of the target
`Gap(eV) = LUMO − HOMO`. Verified numerically on row 0 (`Gap = 6.328555298`, `HOMO = −6.213178962`,
`LUMO = 0.115376336`):

| Column | Formula | Value on row 0 |
| --- | --- | ---: |
| `ChemicalPotential(eV)` | (HOMO + LUMO)/2 | −3.048901313 |
| `ChemicalHardness(eV)` | (LUMO − HOMO)/2 = Gap/2 | 3.164277649 |
| `ChemicalSoftness(1/eV)` | 1/hardness = 2/Gap | 0.3160278935434215 |
| `Electronegativity(eV)` | −(HOMO + LUMO)/2 | 3.048901313 |
| `ElectronAffinity(eV)` | −LUMO | −0.115376336 |
| `IonizationPotential(eV)` | −HOMO | 6.213178962 |
| `ElectrophilicityIndex` | μ²/(2η) | 1.468865922582814 |
| `NucleophilicityIndex` | 1/ω | 0.6807973312102081 |

**None of them is used as a feature anywhere in this package.** Features are computed from `SMILES`
alone (Mordred descriptors, or Mordred + fingerprints in the `*-MF` groups), and
`core/data_processing.py` reads only `SMILES`, `Gap(eV)`, `Y_number`, `C_number`, `Status`,
`A_number` and `B_number`. The columns are kept in the CSV because they document the electronic
structure of each candidate. If you extend the pipeline, do not feed them to a model — a gap
regressor trained on `ChemicalHardness` would be predicting the answer from the answer.

## 2. Feature caches

Both caches are produced by `../prepare_features.py` from `Data-20261012.csv` and store **raw**
(unstandardised, unfiltered) descriptor values. Constant and near-zero-variance columns are dropped
later, per run, by `run_pipeline.py` — which is why 1,613 raw Mordred columns become a few
hundred model inputs and why `filtered_feature_names.json` differs between runs.

### The `.meta.json` contract

| Key | Meaning |
| --- | --- |
| `schema_version` | `1` |
| `raw_descriptors` | `true` — values are neither scaled nor filtered |
| `data_sha256` | SHA-256 of `Data-20261012.csv` at build time |
| `cache_sha256` | SHA-256 of the cache CSV itself |
| `samples` | 1,734 records: `{source_row, source_smiles, Gap(eV), Y_number, C_number}` |
| `columns` | Ordered feature names: 1,613 (Mordred) / 9,972 (Mordred + fingerprints) |
| `descriptor_smiles` | The 1,734 SMILES strings actually featurised, in cache row order |
| `use_fingerprints` | `false` for the Mordred cache, `true` for the fingerprint cache |
| `versions` | python 3.8.20, numpy 1.23.5, pandas 1.5.3, rdkit 2024.03.5, mordred 1.2.0 |

A cache's row order is the position order used by `splits-20261021.json`, and `source_row` is the
0-based record index in the **raw** CSV — it runs over 0…1859 with 1,734 strictly increasing values,
so a cache row can be traced back past the filter.

`../analysis/check_cache_integrity.py` re-derives all of that. Run against this package it prints
`cache shape=(1734, 1613)`, both hashes `ok`, `1734/1734` SMILES reparsed, `0` heavy-atom
differences, and exact matches on `nHBAcc`, `nHBDon`, `nRing`, `nRot` and `nHetero`. Two lines print
`DIFF` by design: `MW` at the 5e-3 relative level, and `TopoPSA`, which is not the same quantity as
RDKit's `CalcTPSA` (Mordred counts S and P, RDKit's default does not). Those are version artefacts of
Mordred 1.2.0 on RDKit 2024.03.5, not corruption.

### Regenerating

```bash
# Mordred cache (needs the mordred 1.2.0 environment: ../environment-features.yml)
python prepare_features.py --data data/Data-20261012.csv \
    --output data/Data-20261012_raw_features.csv

# Fingerprint cache (much slower: RDKit fingerprints for 1,734 molecules x 5 families)
python prepare_features.py --data data/Data-20261012.csv \
    --output data/Data-20261012_raw_features_fp.csv --fingerprints
```

Mordred is a frozen dependency: a different `mordred`/`rdkit` pair changes some descriptor values in
the fourth decimal, which shifts CV MSE slightly. **Use the shipped caches to reproduce the numbers
in this package**; regenerate only when you are deliberately testing version sensitivity.

## 3. `splits-20261021.json` — the frozen splits

One file, three splits, one seed. Every run in `../experiments/` consumed it through
`--split-file data/splits-20261021.json --split-name {random|scaffold|meso}`.

```jsonc
{
  "schema_version": 1,
  "data_sha256": "b4fc2228…",
  "samples": [ { "source_row": 0, "source_smiles": "…", "Gap(eV)": 6.328555298,
                 "Y_number": 1, "C_number": 0 }, … ],   // 1,734 entries, position order
  "smoke": false,
  "seed": 42,
  "split_selection": "…",                                  // how the 20 % test sets were chosen
  "splits": {
    "random":   { "train_positions": […], "test_positions": […], "folds": [ {…} × 5 ],
                  "train_A": […], "test_A": […], "test_fraction": 0.2001 },
    "scaffold": { … }, "meso": { … }
  }
}
```

### The three axes

| Split | Test construction | Train / test | Held-out `A` scaffolds | First fold | What it measures |
| --- | --- | ---: | --- | ---: | --- |
| `random` | Random 20 % — `train_test_split(test_size=0.2, random_state=42)` | 1,387 / 347 (20.01 %) | none: all 18 `A` groups on both sides | 1,109 / 278 | Interpolation inside the design space |
| `scaffold` | Whole `A` scaffolds held out — 200 `GroupShuffleSplit` candidates, the one closest to 20 % by count wins | 1,383 / 351 (20.24 %) | **4** (`A` = 2, 3, 14, 18) | 1,118 / 265 | Extrapolation to unseen cores |
| `meso` | Whole `B` meso substituents held out (`B00` kept on the training side) | 1,398 / 336 (19.38 %) | 16 `A` groups on the test side (A13, A14 absent) | 1,168 / 230 | Extrapolation to unseen meso substitution |

Cross-validation inside each split is five-fold over the same grouping key:

| Split | Splitter | Fold train/valid sizes |
| --- | --- | --- |
| `random` | `KFold(5, shuffle=True, random_state=42)` | (1,109/278) (1,109/278) (1,110/277) (1,110/277) (1,110/277) |
| `scaffold` | `GroupKFold(5)` over `A_number` | (1,118/265) (1,123/260) (1,120/263) (1,085/298) (1,086/297) |
| `meso` | `GroupKFold(5)` over `B_number` | (1,168/230) (1,079/319) (1,084/314) (1,181/217) (1,080/318) |

The `split_selection` field states the protocol verbatim:

> `200 candidates; closest to 20% by count; first tie; no targets | meso: GroupShuffleSplit(200, seed 42) over B_number, closest to 20%, B00 kept on the training side so the split isolates the meso axis; inner CV = GroupKFold(5) over B_number`

The recorded string covers all three axes in one line: the `random` split is a plain
`train_test_split`, while the `scaffold` and `meso` halves describe the 200-candidate
`GroupShuffleSplit` search. Candidates are generated **without looking at the targets**
(`core/experiment_setup.py:49`, `GroupShuffleSplit(n_splits=200, test_size=0.2, random_state=42)`),
and a candidate is admissible only if its test fraction lands in [0.15, 0.25], the training side keeps
at least 5 `A` groups and the test side at least 2 (`core/experiment_setup.py:52-60`), so test-set
selection carries no label information. `test_fraction` is recomputed as
`len(test) / len(data)` (`core/experiment_setup.py:78`) rather than trusted from the generator.

### Using it

```bash
python run_pipeline.py SMILES \
    --data data/Data-20261012.csv \
    --split-file data/splits-20261021.json --split-name meso \
    --run-name my_meso_run --feature-mode mixed
```

`load_split_manifest` (`core/experiment_setup.py:96`) checks `data_sha256` against the CSV you
passed, so a mismatched table fails loudly instead of silently reusing stale positions. The
`experiments/` runs additionally record `train_source_rows`/`test_source_rows` in their
`run_metadata.json`, which is how `../analysis/build_four_group_comparison.py` proves that the six
runs really shared one split per axis.

### Regenerating

The `random` and `scaffold` splits come from the split builder in `core/experiment_setup.py`; the
`meso` split was appended by `../analysis/make_b_split.py`, a thin wrapper over the
`B_number`-grouped construction described above. Regeneration reproduces identical positions only if
`data_sha256` and `seed` are unchanged.

## 4. Verifying this directory

```bash
python ../analysis/check_cache_integrity.py
```

The script re-reads every file against its `.meta.json` (column order, row count, source
history) and re-parses all 1,734 SMILES; it exits non-zero on any mismatch.
